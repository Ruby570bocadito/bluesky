## Detalle por corrección

### 18. Auth token opcional en dashboard web — **Media** (NUEVO)

**Componente:** `bluesky/web/app.py` + `bluesky/cli.py`

**Descripción:**
El informe de z_pulimiento (ronda 1) confirmó que exponer el dashboard
con `--host 0.0.0.0` permite a cualquiera en la red lanzar escaneos/ataques
vía API. z_pulimiento lo dejó como decisión de diseño para el Director;
yo lo he implementado como feature opt-in.

**Severidad:** Media (no es bug, es mitigación de riesgo al exponer el
dashboard).

**Solución aplicada:**

1. `create_app(debug, auth_token)` acepta un nuevo parámetro `auth_token`.
   Si se proporciona, se almacena en `app.state["auth_token"]`.
2. Nuevo `@app.before_request` que se ejecuta **ANTES** del middleware
   CSRF:
   - Si `auth_token` es None → behavior actual (sin auth).
   - Si `auth_token` está configurado → TODAS las peticiones deben
     incluir el token en:
     - Header `Authorization: Bearer <token>` (recomendado para API), o
     - Query param `?token=<token>` (para URLs de navegador).
   - Comparación con `hmac.compare_digest()` (timing-safe, evita timing
     attacks).
   - 401 JSON para peticiones `/api/*`, 401 text/plain para páginas HTML.
3. `run_web_server(auth_token)` propaga el parámetro.
4. `cmd_web` en `cli.py` acepta `--token <TOKEN>`.
5. **Warning de seguridad**: si `--host` no es localhost y no se
   proporciona `--token`, se imprime advertencia al arrancar.
6. **Auto-token en navegador**: si `--open` y hay token, la URL que se
   abre en el navegador incluye `?token=<TOKEN>` para que el primer GET
   no devuelva 401.

**Archivos modificados:**
- `bluesky/web/app.py` (middleware auth + run_web_server)
- `bluesky/cli.py` (flag --token en cmd_web)

**Cómo usarlo:**
```bash
# Exponer dashboard en la red local CON auth:
bluesky web --host 0.0.0.0 --token mySecret123

# Sin auth (solo localhost, default):
bluesky web  # behavior actual, sin cambios
```

**Cómo verificar que está corregido:**
```bash
python -m pytest tests/test_security_bugs.py::TestWebTokenAuth -v
# 9 tests cubren: sin token, token en header, token en query,
# token incorrecto, HTML 401, POST con token, orden auth>CSRF,
# timing-safe comparison.
```

### 19. Wildcards `all`/`*`/`broadcast` bloqueados por validación MAC — **Media**

**Componente:** `bluesky/core/engine.py` (método `BaseModule.check_prerequisites`)

**Descripción del bug:**
Mi validación MAC global (ronda 2) bloqueaba targets legítimos como
`"all"`, `"*"`, `"broadcast"` que `btspam` admite para atacar a todos
los dispositivos detectados. El `target.lower() in ("all", "*", "broadcast")`
en `btspam.run()` se ejecuta DESPUÉS de `check_prerequisites()`, así que
mi validación bloqueaba antes de llegar al check de wildcards.

**Severidad:** Media (bug funcional introducido por mi ronda 2; rompe
`btspam` con `target="all"`).

**Causa raíz:**
- La validación MAC global no contemplaba wildcards legítimos.
- `btspam` define `TARGET: "vacío = todos"` en `module_options`, pero
  también admite `"all"`, `"*"`, `"broadcast"` como valores explícitos.

**Solución aplicada:**

`BaseModule.check_prerequisites` ahora admite un set de wildcards
legítimos además de MAC válida:
```python
_wildcards = {"all", "*", "broadcast"}
if str(target_value).lower() not in _wildcards and not is_valid_mac(target_value):
    return False, (f"Target '{target_value}' no tiene formato MAC válido ...")
```

Case-insensitive: `"ALL"`, `"All"`, `"all"` se aceptan igual.

**Archivos modificados:**
- `bluesky/core/engine.py`

**Cómo verificar que está corregido:**
```bash
python -m pytest tests/test_security_bugs.py::TestBaseModuleWildcards -v
# 6 tests cubren: all, *, broadcast, ALL (uppercase),
# --evil-flag bloqueado, shell injection bloqueado.
```

**Componente:** `bluesky/modules/scanners/vuln_scanner.py`

**Hallazgos:**

   datos interpolados se escapan con `utils.format.esc()`).

6. **No hay `shell=True`, `os.system`, `eval`, `exec`**.

**Conclusión:** `vuln_scanner.py` está seguro tras el fix de XSS de la
