## Detalle por corrección

### 9. `cmd_report` construye mal el payload del Reporter — **Alta**

**Componente:** `bluesky/cli.py` (función `cmd_report`)

**Descripción del bug:**
`cmd_report` pasaba `session.summary()` al `Reporter`, pero `Reporter`
espera un payload con claves:
- `session{name, date, duration, environment}`
- `targets[]`
- `results[]`

Mientras que `session.summary()` devuelve:
- `name, created_at, updated_at, total_targets, total_results, targets[]`

Sin `session{}` ni `results[]`, el reporte salía con "Session: N/A,
Date: N/A" y la sección "Attack Results: 0" aunque la sesión tuviera
resultados cargados.

**Bug adicional detectado al corregir:** el flag `--txt` era ignorado
si la config tenía `report_format: html` (default). Solo se sobrescribía
para `--html` y `--json`, no para `--txt`.

**Severidad:** Alta (el entregable principal de la CLI estaba roto).

**Causa raíz:**
- Mal acoplamiento entre `Session.summary()` (pensado para UI/consola)
  y `Reporter` (pensado para serialización a HTML/TXT/JSON).
- Falta de tests de integración `cmd_report` ↔ `Reporter`.

**Solución aplicada:**

1. `cmd_report` ahora construye un `reporter_payload` explícito con las
   claves que `Reporter` espera:
   ```python
   reporter_payload = {
       "session": {"name": ..., "date": ..., "duration": "", "environment": ""},
       "targets": session.targets if isinstance(..., list) else [],
       "results": session.results if isinstance(..., list) else [],
   }
   reporter = Reporter(reporter_payload)
   ```
2. Añadido `elif ns.txt: report_fmt = "txt"` para que `--txt` sobrescriba
   la config.

**Archivos modificados:**
- `bluesky/cli.py`

**Cómo verificar que está corregido:**
```bash
python -c "
import sys, os, tempfile
sys.path.insert(0,'.')
from bluesky.utils.config import BlueskyConfig
BlueskyConfig.reset_instance()
with tempfile.TemporaryDirectory() as td:
    os.environ['HOME'] = td
    BlueskyConfig.reset_instance()
    from bluesky.core.session import Session
    s = Session(name='default')  # usa td/.bluesky/sessions/
    s.add_target('AA:BB:CC:DD:EE:FF', 'Test Device', -65)
    s.add_result('bluejacking', 'AA:BB:CC:DD:EE:FF', True,
                 data={'msg':'sent'}, error=None)
    s.add_result('knob', 'AA:BB:CC:DD:EE:FF', False, data={}, error='no hw')
    BlueskyConfig.reset_instance()
    from bluesky.cli import cmd_report
    out = os.path.join(td, 'report.txt')
    cmd_report(['--txt', '-o', out])
    content = open(out).read()
    assert 'bluejacking' in content and 'knob' in content
    print('OK')
"
```

### 10. `console.do_report` mismo bug + path traversal — **Alta**

**Componente:** `bluesky/console.py` (método `do_report`)

**Descripción del bug:**
Mismo problema que `cmd_report`: pasaba `session.summary()` modificado
al Reporter. Aunque añadía `summary["session"] = {...}`, no incluía
`results[]`, así que la sección de resultados quedaba vacía.

**Bug adicional detectado al corregir:**
- `fmt = a[2:]` aceptaba cualquier valor como formato sin whitelist.
  Un usuario REPL podía hacer `report --../../../tmp/evil` y el `fmt`
  terminaba como parte del filename (`bluesky_report_default.../../../tmp/evil`).
- `filepath = output_dir / filename` permitía path traversal si el
  usuario pasaba `../../tmp/evil.html` como filename.

**Severidad:** Alta (REPL interactivo, pero reportes rotos + traversal).

**Causa raíz:**
- Misma que #9: mal acoplamiento `Session.summary()` ↔ `Reporter`.
- Falta de whitelist en parseo de `--format`.
- Falta de comprobación `resolve().parents` en filepath.

**Solución aplicada:**

1. `do_report` ahora construye `reporter_payload` con `session{}`,
   `targets[]` y `results[]` (mismo patrón que `cmd_report`).
2. Whitelist de formatos: `if candidate in ("html", "json", "txt")`
3. Validación de path: `resolved = filepath.resolve()` y comprobar
   que `base (output_dir.resolve())` está en `resolved.parents`.

**Archivos modificados:**
- `bluesky/console.py`

**Cómo verificar que está corregido:**
```bash
python -m pytest tests/test_security_bugs.py::TestCmdReportPayload -v
```

### 11. Refactor: validación MAC unificada en un único helper — **Baja**

**Componente:** `bluesky/utils/network.py` + `bluesky/core/engine.py` + `bluesky/utils/termux_backend.py`

**Descripción del problema:**
Tras las rondas 1 y 2, teníamos 3 implementaciones duplicadas del
mismo regex de validación MAC:
- `utils/network.py:mac_valid()` (original)
- `core/engine.py:is_valid_mac()` (añadido en ronda 2)
- `utils/termux_backend.py:_is_valid_mac()` (añadido en ronda 2)

Code smell que dificulta mantenimiento.

**Severidad:** Baja (no era bug, era deuda técnica).

**Solución aplicada:**

1. `utils/network.py:mac_valid()` es ahora la **fuente única de verdad**.
   Se mejoró para tolerar None/otros tipos sin lanzar TypeError.
2. `core/engine.py:is_valid_mac()` y `utils/termux_backend.py:_is_valid_mac()`
   ahora delegan en `mac_valid()` mediante lazy import (evita circular
   import entre `core` y `utils`).
3. Test `TestMacValidationUnification` verifica que las 3 funciones
   devuelven lo mismo para 6 casos representativos.

**Archivos modificados:**
- `bluesky/utils/network.py` (mejorada tolerancia a tipos)
- `bluesky/core/engine.py` (delega en network)
- `bluesky/utils/termux_backend.py` (delega en network)

**Cómo verificar que está corregido:**

### 12. 10 módulos sobreescriben `check_prerequisites` sin llamar `super()` — **Media**

**Componente:** 10 archivos en `bluesky/modules/`:
- `exploits/l2cap_fuzz.py`
- `exploits/rfcomm_shell.py`
- `attacks/btspam.py`
- `attacks/sweyntooth.py`
- `attacks/bluebugging.py`
- `attacks/bluefrag.py`
- `attacks/crackle.py`
- `attacks/bluffs.py`
- `attacks/knob.py`
- `attacks/btlejack.py`

**Descripción del bug:**
Cada uno de estos módulos sobreescribe `check_prerequisites()` con
lógica específica (verificar `rfcomm`/`sdptool`/`scapy` disponible)
pero **NO** llama a `super().check_prerequisites()`. Eso significa que
la validación global de MAC (añadida en ronda 2 en `BaseModule`) NO se
aplica a estos módulos.

Aunque `subprocess.run` con argv separado evita shell injection, un
target malicioso como `--evil-flag` se pasaría como argumento a
`sdptool browse --evil-flag` o `rfcomm bind /dev/rfcomm0 --evil 1`,
pudiendo ser interpretado como flag.

**Severidad:** Media (defensa en profundidad; cierra patrón peligroso
aunque no explotable directamente hoy).

**Causa raíz:**
- Falta de disciplina OOP: los overrides no llaman a `super()`.
- La validación MAC global se añadió DESPUÉS de que los módulos
  existieran, y nadie actualizó los overrides.

**Solución aplicada:**

Añadido al inicio de cada `check_prerequisites` override:
```python
# Validación MAC global (BaseModule)
ok, msg = super().check_prerequisites()
if not ok:
    return False, msg
```

Además, actualicé las descripciones de `TARGET` en `btlejack.py` y
`bluefrag.py` para añadir "(opcional ...)" — esto permite que la
heurística de `BaseModule.check_prerequisites` no exija target cuando
es legítimamente opcional (modo scan de estos módulos).

**Archivos modificados:**
- `bluesky/modules/exploits/l2cap_fuzz.py`
- `bluesky/modules/exploits/rfcomm_shell.py`
- `bluesky/modules/attacks/btspam.py`
- `bluesky/modules/attacks/sweyntooth.py`
- `bluesky/modules/attacks/bluebugging.py`
- `bluesky/modules/attacks/bluefrag.py` (descripción TARGET actualizada)
- `bluesky/modules/attacks/crackle.py`
- `bluesky/modules/attacks/bluffs.py`
- `bluesky/modules/attacks/knob.py`
- `bluesky/modules/attacks/btlejack.py` (descripción TARGET actualizada)

**Cómo verificar que está corregido:**

## Auditoría de binarios externos: flags tras `--`

Investigué si las herramientas CLI invocadas (`sdptool`, `hcitool`,
`bluetoothctl`, `rfcomm`, `l2ping`, `termux-bluetooth-*`) interpretan
flags tras un target malicioso.

**Conclusión:** SÍ, son vulnerables a flags como `--evil-flag` si se
pasan como argumento posicional tras `browse`/`info`/`bind`. Esto NO
es un bug de las herramientas (comportamiento getopt estándar) sino
un riesgo si el caller no valida el input.

**Mitigación ya aplicada:** mi validación MAC global en
`BaseModule.check_prerequisites` (ronda 2) + los `super()` calls en
los 10 overrides (ronda 3, esta ronda) cierran este vector. Un
target=`--evil-flag` se bloquea con `"Target '--evil-flag' no tiene
formato MAC válido"` antes de llegar a cualquier subprocess.
