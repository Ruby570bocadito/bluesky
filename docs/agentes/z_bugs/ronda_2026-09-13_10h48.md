## Detalle por corrección

### 4. CSRF en endpoints POST — **Media**

**Componente:** `bluesky/web/app.py`

**Descripción del bug:**
Los endpoints POST (`/api/modules/<name>/run`, `/api/scan`) aceptaban JSON
sin validar el `Origin` o `Referer`. Aunque la app está bindeada a
`127.0.0.1` por defecto, esto no bloquea peticiones CSRF: cualquier web
maliciosa puede hacer un `fetch('http://127.0.0.1:5000/api/scan', {method:'POST', body:'...'})`
que el navegador del usuario enviará con sus cookies/credenciales de
localhost. Un atacante podría:
- Lanzar módulos de ataque contra víctimas BT del auditado.
- Lanzar scans que consuman tiempo o generen tráfico sospechoso.

**Severidad:** Media (no crítica porque la app no maneja sesiones ni
autenticación, pero el vector CSRF es real y silencioso).

**Causa raíz:**
- Falta de middleware que valide el origen de las peticiones mutativas.

**Solución aplicada:**

1. Helper `_is_safe_origin()` en `_register_routes`:
   - Si no hay `Origin` ni `Referer` (caso curl/scripts): permite.
   - Si hay, su host debe coincidir con `request.host`.
   - Cualquier header presente pero sin host parseable → bloquea.
2. Hook `@app.before_request` que aplica la validación a POST/PUT/DELETE/PATCH.
   En caso de fallo, retorna `403 Forbidden` con JSON explicativo y añade
   un log de warning con el origen bloqueado.
3. GET/HEAD no están afectados (idempotentes).

**Archivos modificados:**
- `bluesky/web/app.py`

**Cómo verificar que está corregido:**
```bash
cd /path/to/bluesky
python -c "
import sys; sys.path.insert(0,'.')
from bluesky.web.app import create_app
app = create_app(debug=False); c = app.test_client()

# curl sin Origin → permitido
r = c.post('/api/scan', json={'scanner':'device'})
assert r.status_code != 403, 'curl bloqueado!'

# Origin evil → bloqueado
r = c.post('/api/scan', json={}, headers={'Origin':'http://evil.com'})
assert r.status_code == 403, 'evil origin no bloqueado!'

# Origin mismo host → permitido
r = c.post('/api/scan', json={}, headers={'Origin':'http://localhost'})
assert r.status_code != 403, 'mismo origin bloqueado!'

# GET no afectado
assert c.get('/api/status').status_code == 200
print('OK: proteccion CSRF funciona')
"
```

### 5. Exposición de info sensible en `/api/config` — **Baja/Media**

**Componente:** `bluesky/web/app.py` (endpoint `api_config`)

**Descripción del bug:**
El endpoint devolvía TODA la configuración vía `config.get_all()`:
- `default_target.address` (MAC del target por defecto del usuario)
- `favorites` (lista completa de MACs guardadas por el usuario)
- `module_options` (posiblemente con MACs en overrides)
- `session.last_session` (path del archivo de sesión en disco)
- `platform_info` con `backends` (puede exponer MAC del adaptador local)

Si la app se exponía (por accidente o para acceso desde móvil), era una
fuga significativa de información útil para fingerprinting.

**Severidad:** Baja/Media (requiere que la app esté expuesta, pero la
fuga es real).

**Causa raíz:**
- `get_all()` está pensado para uso interno (tests, exporter); el endpoint
  API no debería devolverlo sin filtrar.

**Solución aplicada:**

El endpoint ahora devuelve solo:
```json
{
  "config": {
    "general": {  // solo claves de UI
      "theme", "log_level", "report_format", "safe_mode", "language"
    },
    "favorites_count": <int>,         // contador, no lista
    "module_options_count": <int>     // contador, no dict
  },
  "platform": {
    "is_root", "is_termux", "is_wsl",
    "os_name", "platform"
    // 'backends' eliminado (contiene info de hardware)
  }
}
```

`default_target`, `favorites`, `module_options` y `session.last_session`
ya no se exponen.

**Archivos modificados:**
- `bluesky/web/app.py`

**Cómo verificar que está corregido:**
```bash
python -c "
import sys, json; sys.path.insert(0,'.')
from bluesky.web.app import create_app
r = create_app(debug=False).test_client().get('/api/config')
data = json.dumps(r.get_json())
assert 'address' not in data, 'default_target.address expuesto!'
assert 'favorites_count' in data
assert 'last_session' not in data
assert 'backends' not in data
print('OK: /api/config filtrado')
"
```

### 6. Inyección PowerShell latente en `hardware.py` — **Baja**

**Componente:** `bluesky/core/hardware.py` (funciones `_check_usb_vendor_windows` y `_check_usb_product_windows`)

**Descripción del bug:**
Ambas funciones interpolaban input en scripts PowerShell con f-strings:
```python
ps_script = f"""
$devices = Get-PnpDevice ... | Where-Object {{
    $_.InstanceId -match '{"|".join(patterns)}'
}}
...
"""
```

Aunque hoy los callers pasan strings hardcoded (`"0a12"`, `"rtl8761"`),
cualquier feature futuro que acepte input del usuario y lo pase por aquí
permitiría inyección de PowerShell. Ejemplo: si `vendor_ids` recibiera
`"0a12';Add-Type ...;'"`, el script resultante ejecutaría código
arbitrario.

**Severidad:** Baja (no explotable hoy, pero patrón peligroso que debía
cerrarse).

**Causa raíz:**
- Construcción de scripts PowerShell vía f-strings en lugar de parámetros
  separados o whitelisting estricto.

**Solución aplicada:**

1. `_check_usb_vendor_windows`: filtra `vendor_ids` con whitelist
   `re.fullmatch(r"[0-9A-Fa-f]+", vid)`. Solo hex válido pasa. Rechaza
   cualquier vendor_id no-hex.
2. `_check_usb_product_windows`: valida `product_name` con whitelist
   `[A-Za-z0-9_-]+`. Rechaza cualquier cosa fuera de ese set.
3. Ambas funciones reescriben el script PowerShell como string estático
   con placeholder `__PATTERNS__` / `__PRODUCT__` que se reemplaza por
   `.replace()` (no f-string), de forma que el contenido ya saneado se
   inserta sin parsing adicional.

**Archivos modificados:**
- `bluesky/core/hardware.py`

**Cómo verificar que está corregido:**
```bash
python -c "
import sys; sys.path.insert(0,'.')
from bluesky.core.hardware import (
    _check_usb_vendor_windows, _check_usb_product_windows)
# Inyección PowerShell → rechazado silenciosamente (devuelve False,
# no ejecuta el script)
assert not _check_usb_product_windows(\"rtl8761';Calc;'\")
assert not _check_usb_vendor_windows([\"0a12';Calc;'\"])
print('OK: inyeccion PowerShell bloqueada')
"
```

### 7. Validación MAC global en `BaseModule` — **Media** (NUEVO)

**Componente:** `bluesky/core/engine.py`

**Descripción del bug:**
Ninguno de los ~20 módulos de ataque/scanner valida que `target` sea una
MAC válida antes de pasarlo a `subprocess.run([..., "info", target])`.
Aunque `subprocess.run` con argv separado evita shell injection, un
target malicioso como `"--evil-flag"` o `"; rm -rf $HOME"` (si se pasa
junto a un binary que interprete flags tras `--`) podría ser interpretado
como flag adicional por `sdptool`, `hcitool` o `bluetoothctl`.

Más grave aún: en `termux-bluetooth-pair <address>`, si la tool Termux
acepta flags tras la MAC, un attacker podría inyectar argumentos.

**Severidad:** Media (defensa en profundidad; no explotable directamente
hoy, pero cierra un patrón peligroso).

**Causa raíz:**
- Ausencia de helper centralizado para validar MAC.
- Cada módulo hace su propio check mínimo (si lo hace).

**Solución aplicada:**

1. Nuevo helper `is_valid_mac(address)` exportado desde `core/engine.py`
   con regex `^[0-9A-Fa-f]{2}([:-][0-9A-Fa-f]{2}){5}$`.
2. `BaseModule.check_prerequisites()` ahora valida que, si se
   proporciona `target` (vía `self.target` o `self.options["TARGET"]`),
   tenga formato MAC válido. Si no, retorna `(False, "Target '...' no
   tiene formato MAC válido...")`.
3. Heurística backward-compatible: si la descripción de `TARGET` contiene
   "opcional" (p. ej. Crackle: "MAC del dispositivo (opcional para
   filtrado)"), no se exige target presente. Solo se valida formato si
   target está realmente proporcionado.

**Archivos modificados:**
- `bluesky/core/engine.py`

**Cómo verificar que está corregido:**
```bash
python -c "
import sys; sys.path.insert(0,'.')
from bluesky.core.engine import BaseModule, is_valid_mac

assert is_valid_mac('AA:BB:CC:DD:EE:FF')
assert is_valid_mac('aa-bb-cc-dd-ee-ff')
assert not is_valid_mac('--evil-flag')
assert not is_valid_mac('AA:BB:CC:DD:EE:FF; rm -rf /')
assert not is_valid_mac('')

class TestMod(BaseModule):
    name = 'test'
    module_options = {'TARGET': 'MAC objetivo'}
    def run(self, target='', options=None):
        return {'success': True, 'data': {}, 'error': None}

# MAC válida → ok
assert TestMod(target='AA:BB:CC:DD:EE:FF').check_prerequisites()[0]
# MAC inválida → bloqueado
assert not TestMod(target='--evil-flag').check_prerequisites()[0]
# MAC vacía → bloqueado (requerido)
assert not TestMod(target='').check_prerequisites()[0]
print('OK: validacion MAC global funciona')
"
```

### 8. Validación MAC en Termux backend — **Media** (NUEVO)

**Componente:** `bluesky/utils/termux_backend.py`

**Descripción del bug:**
Las funciones `get_device_info`, `pair_device`, `unpair_device`,
`connect_device`, `disconnect_device` aceptaban `address: str` y lo
pasaban a `_run_termux_api(cmd, address)` sin validar formato. Aunque
`subprocess.run` con argv separado evita shell injection, un plugin
hostil o input malicioso podría pasar `--evil-flag` como address y que
`termux-bluetooth-pair --evil-flag` hiciera algo inesperado.

**Severidad:** Media.

**Causa raíz:**
- Ausencia de validación de input en funciones públicas del backend.

**Solución aplicada:**

1. Nuevo helper privado `_is_valid_mac(address)` (mismo regex que en
   `core/engine.py`).
2. Cada una de las 5 funciones que toman `address` valida con el helper
   antes de llamar a `_run_termux_api`. Si no pasa, retorna `None` o
   `False` según el tipo de retorno y hace `log.warning`.

**Archivos modificados:**
- `bluesky/utils/termux_backend.py`

**Cómo verificar que está corregido:**
```bash
python -c "
import sys; sys.path.insert(0,'.')
from bluesky.utils.termux_backend import pair_device, _is_valid_mac
assert _is_valid_mac('AA:BB:CC:DD:EE:FF')
assert not _is_valid_mac('--evil')
# pair_device con MAC inválida retorna False sin llamar subprocess
assert not pair_device('--evil')
print('OK: termux backend valida MAC')
"
```

## Bugs/vulnerabilidades detectados pero NO corregidos aún

### 9. `Session.list_sessions()` no filtra por extensión — **Baja**

**Componente:** `bluesky/core/session.py`

**Descripción:**
`list_sessions()` hace `path.glob("*.json")` y retorna `f.stem`. Si un
atacante con acceso de escritura al directorio de sesiones coloca un
`.json` con nombre malicioso (p. ej. `../../../etc/passwd.json`), el
nombre aparecería en la lista de sesiones y podría confundir al usuario.

**Severidad:** Baja (requiere acceso de escritura al directorio, lo que
ya implica compromiso total).
**Motivo de no corregir:**
El `glob` de `pathlib` ya no sigue `..` en el patrón, y el `_stem`
solo devuelve el nombre sin extensión. No hay traversal real. La única
improvement sería validar que el stem cumple el whitelist (como ya hace
`_sanitize_session_name`). Dejar para refactor del Director.

## Recomendaciones de seguridad generales para el resto de agentes

### Para el agente **Implementaciones**

1. **`is_valid_mac()` ya está disponible en `bluesky.core.engine`**:
   importadlo y usadlo en cualquier nuevo módulo que acepte MACs.
2. **No interpoléis strings en PowerShell** sin whitelist estricto.
   Seguir el patrón de `_check_usb_vendor_windows` (corregido en esta
   ronda): placeholder `__X__` + `.replace()`, nunca f-string.
3. **Cualquier nuevo endpoint POST debe pasar el middleware CSRF**
   automáticamente (ya cubierto por `@app.before_request`). Si añadís
   un endpoint exento (p. ej. webhook), hacedlo explícito y documentado.

### Para el agente **Pulimiento**

1. Considerar extraer `_is_valid_mac` de `termux_backend.py` y
   `is_valid_mac` de `engine.py` a un único helper en
   `bluesky/utils/network.py` (que ya tiene `mac_valid()`). Hay
   3 implementaciones del mismo regex: code smell.
2. Los tests `test_qa_round2.py::TestReporterHtmlEscaping` cubren
   `Reporter.to_html()`. Sería valioso añadir tests equivalentes para:
   - `Autopilot._phase_report()` (corregido en ronda 1).
   - Middleware CSRF (corregido en esta ronda): tests para Origin
     válido, Origin malicioso, sin Origin.
   - `is_valid_mac()` y `BaseModule.check_prerequisites()` con MAC
     maliciosa.
3. Considerar añadir `pytest -m "not requires_external"` para marcar
   tests que requieren `crackle`/`scapy` y poder excluirlos del CI
   mínimo.

### Para el **Director**

1. **Política de secretos**: reitero la recomendación de la ronda 1.
   El operador compartió un PAT de GitHub en texto plano. Requiere:
   - Añadir a `CONTRIBUTING.md` que nunca se compartan tokens por chat.
   - Documentar en `README.md` el uso de GitHub Secrets para CI.
2. **CI**: añadir un job que instale `flask` antes de correr tests web.
   Actualmente los tests `test_web.py` fallan en CI si no se instala
   `flask` (33 tests false-negative).
3. **Decisión de diseño pendiente**: ¿debería el dashboard web pedir
   confirmación explícita antes de ejecutar módulos de ataque con
   `severity=critical` (blueborne, autopilot, bluebugging)? Como
   mitigación UX frente a clicks accidentales o CSRF residual.
